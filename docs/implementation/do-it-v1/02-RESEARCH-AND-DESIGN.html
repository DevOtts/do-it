The short version
  1. do-it is a small deterministic spine plus a thin conductor, not a smart manager agent. Code owns state, gates, resume and the ledger. Models do the work inside stages. The reference video, the Engine squad model and the benchmark literature all land on this shape.
  2. LLM-agnostic means a file contract, not a plugin API. Stages are SKILL.md files, state is .do-it/ JSON on disk, and a dependency-free CLI is the only writer. Claude Code, opencode, Codex, DeepSeek-through-opencode and Engine each get a thin adapter.
  3. Your plugins are not drivable yet. Every handoff today is you pasting a prompt, and only plan-it has exit codes. The first deliverable is a shared result.json envelope in each plugin, before any orchestration.
  4. The design target is your three real pains: "done" that is not done (the most repeated complaint), token burn from long-lived contexts, and glue work (kickoff pastes, limit-resume pings, owner questions, deploy collisions).
  5. Token economy is a core job of do-it, with four levers in this order: keep contexts small, route each slice to the cheapest tier that can pass its test, split work so small models take the parts that do not need a big one, and shape every brief so the provider cache hits. The success metric is tokens per VERIFIED DoD row (section Tokens).
  6. Two correction notes: the video is a talk about AI Developer Workflows, not a demo of Engine squads. And the do-it-revision-brainstorm transcript no longer exists, only its ledger card, so its checklist is reconstructed (see Caveats).

What the research found

Video

Router plus fixed pipelines

IndyDevDan's talk builds up an AI Developer Workflow step by step: build agent, code gates that loop failures back, a test agent, a planner, worktrees, sandboxes, a ticket board where code moves status, a hotfix path with an approve/reject node, and a "factory router" that picks a workflow per ticket type. The router can be one LLM call or plain code (19:40).

Engine

Squad = pipeline of steps

The conductor persona only sets a default tier. The versioned pipeline definition conducts: steps of type persona, checkpoint, decision, render, publish, with portable tiers (powerful/balanced/cheap), a one-hop consumes_previous handoff, and review rounds capped at 2.

Benchmarks

Single writer, disk memory

Multi-agent runs cost about 15x chat tokens (Anthropic). Parallel writer swarms still fail (Cognition, Apr 2026). What works: one writer, read-only subagents, clean-context reviewers, state on disk, results recorded once.

Your sessions

Same shape every time

brain-dump, plan, ratify, fresh build session, review loop, deploy train, conclude. You repeat the glue by hand: pasting kickoffs, resuming after limits, asking "is X still running?", and chasing items that never reached 0-done.

What the video does and does not give us

It gives us a grammar: three actor types (human, agent, code), reliability ordered code > engineer > agent, humans only at the two ends, and failure edges that loop back to the build agent. We reuse that grammar for every diagram here. It does not show personas, squads, or a manager delegating by chat. That part of your idea comes from Engine itself, so the squad design below is taken from Engine's schemas, not from the video.

The founding failure is already documented. 01-TOKEN-DISCIPLINE.md measured the 2026-09-26 runs: a coordinator grew to 857K context, a finished planning session kept polling (64M tokens), ten spec'd workers were spawned on the top tier. Cost tracks the sum of context read on every call, so long-lived conductors are the leak. do-it inherits those rules as gates (section Design).

Ten lessons that shape the design

  1. One writer at a time; many read-only readers and an independent reviewer.
  2. Disk is the memory. The context window is a cache.
  3. Record each stage result once. Resume skips what is recorded.
  4. Handoffs are written briefs with objective, output format, boundaries.
  5. Gates are data records with exit codes, not prose promises.
  6. "Done" is a ledger lookup checked by someone who did not write the code.
  7. Scale effort to the size of the task; a typo fix must not spin up a swarm.
  8. Pick the model per stage; escalate on failure rather than pre-paying.
  9. Git is the undo and the audit trail.
  10. Do not depend on any host's experimental feature.

Evidence quality is uneven. The Anthropic, Cognition (Apr 2026), Claude Code, agentskills.io and superpowers sources were read directly. Kiro, BMAD, Spec Kit, Aider, Cline, Devin, Codex and CrewAI details come from secondary sources and need re-checking before we rely on flag names or pricing. How do-it would work

Five layers, from the host down to the disk. Everything above the disk layer can be swapped without touching the state.

Host adaptersClaude Code (plugin, hooks, claude -p --bare) · opencode (JS plugin on session.idle) · Codex (codex exec) · generic runner for any CLI including DeepSeek via opencode or OpenRouter · Engine (compile the squad file into a pipeline_definition). Each adapter declares what it can do: hooks, subagents, resume.
ConductorA thin T2 persona with a context ceiling. It reads do-it next, spawns the stage persona with a brief of 8K tokens or less, and goes back to sleep. It restarts from state files at the ceiling. It never reads whole files or relays worker chatter.
Stage personasPlain markdown files with name, description, tier, tools frontmatter, like Engine's engine-verifier.md: intake, planner, builder, reviewer, deployer, concluder, reconciler, and an independent verifier. Each wraps one stage plugin skill.
Spine CLIOne dependency-free do-it script, the only writer of run state. Commands: start, next, record, gate, park, resume, status --json, meter, doctor. Exit codes 0 ok · 1 failed · 2 needs human · 3 blocked or limit. Where hooks exist it is called from them; where they do not, it is called by the conductor checklist.
DiskOne folder, .do-it/, holds all machine state and reports for every stage (layout in section Behaviors, part 4). Host config such as .claude/, .agents/, .opencode/ and .secrets/ stays where the host expects it.

Rules the spine enforces, from your own corrections

Tiers

Every spawn names a tier. T1 needs a written reason or is downgraded. Conductor defaults to T2, never the top model. A failed contract re-runs one tier up and the escalation is logged. Tiers map to models per provider in a config asked for once.

Context

Warn at 150K or 40% of window, block tool calls at 250K or 60% until a checkpoint and reset. Resuming from state files must reproduce goal, DoD and next action. No wake-up on a context above 50K.

Done

A DoD row is VERIFIED only with an evidence reference. Builder output starts at IMPLEMENTED-NOT-VERIFIED. Conclude refuses to close with an unaccounted row, a live worker, or a pending wake-up.

Humans

Four gate kinds: plan ratify, owner gates (prod flag, credentials, spend, destructive, client-facing), attended checks, and review rounds past the cap. All questions from all stages collect into one numbered owner pack. Your terse reply is parsed and routed back.

Limits

On a usage-limit signal the run parks with a resume note and schedules itself. A fresh context starts at each wake. The first wake after the reset resumes from state.json, and no run waits for you to return.

Deploys

The deploy stage takes the router lock first, canaries on the lowest-risk target, and requires every leg the adapter declares. A green image with a missing leg is not a closed deploy.

Mapping to an Engine squad

The same lifecycle.squad.yaml compiles to a pipeline_definition: persona steps stay, checkpoint becomes a Mission Control card, code steps become render/publish capability calls, tiers pass through unchanged. The persona files become persona-agent documents. What does not carry over without Engine: the database, dispatcher, Kubernetes jobs, Mission Control UI, seats and billing. Note that Codex is typed but refused as a backbone, and opencode is not a backbone, so "Engine runs do-it" needs a runner-side decision (see Decisions).

Four behaviors that made your runs good, made mechanical

These come from how you described what works. Each one is currently kept alive by you (a nag, a rule you repeat, a folder you tidy), and the design moves it into the spine so it survives without you.

1. Plan once, ask once

What works today: the plan-it run that asks every question up front, writes the whole plan, and hands you one document of decisions that already carry a recommendation. You approve or disagree. It fails when the plan stops halfway and asks questions in pieces.

  • Readiness verdict. Planning ends only with .do-it/plan/READINESS.json: every decision is RESOLVED (you answered) or DEFAULTED (recommendation recorded, marked reversible or not); the access preflight passed (credentials, tools, repos and hosts probed live, not assumed); no build slice depends on an answer from you. Build cannot start without it.
  • One decision document. .do-it/plan/DECISIONS.md lists each decision with the options, the recommendation and the reason, so your reply is "approve all except 4 and 7".
  • No mid-run questions. A question that surfaces during build is decided by its recorded recommendation, written to the decision log, and shown in the owner pack at the end. The exception is an owner gate (production flag, credentials, spend, destructive, client-facing): only that slice parks, the others continue.

2. Run to the finish line

What you observed: with everything pre-answered and access granted, a session still stopped after a wave and left the rest. Asking "why are these still not in 0-done?" made it continue. My reading, which fits your ledger (it is the most repeated complaint) but has not been tested: the model needs a visible end state to pull toward, and "do everything" lets it declare victory at the first natural pause. So do-it asks that question itself, every time, in code.

Finish-line board

At plan handoff the spine writes .do-it/finish-line.json: every wave, package and DoD row. A row is terminal only as DONE (evidence recorded and the package archived to 0-done), PARKED with an owner question, or BLOCKED with a reason.

Stop-gate

The run cannot end a turn or a session while a row is non-terminal and no blocker exists. It answers with the board: "6 of 9 rows non-terminal; next is wave 3". Claude Code uses a Stop hook; other hosts use the conductor checklist.

Waves scheduled by code

do-it next returns the next runnable wave. The conductor does not decide whether to continue, so finishing a wave never reads as finishing the job.

Board on every wake

The board is injected on each resume in about 300 tokens, so the end state is always in view. That is far cheaper than the context it saves.

Guard against its own loop. The stop-gate refuses at most N times in a row without progress, then parks the run and asks you, so it cannot spin forever on a row that is genuinely stuck.

3. Convergence control for review loops

Keep: the reviewer creates the roteiro, another agent (ideally) runs it, the builder fixes, and the cycle repeats. This is where quality jumped. Add: the exit condition, which neither the reviewer (always finds something) nor the builder (wants to be done) can judge, so it sits in do-it.

4. One home for everything: .do-it/

Your Engine-Core root currently carries .build-it-reports, .fable-it-reports, .plan-it, .review-it and .taskstate, next to the host folders. In the do-it family every stage writes under one folder.

                         briefs/  results/  owner-pack.md

  build/                 was .build-it-reports/, .fable-it-reports/, .taskstate/

  deploy/                run logs, leg results
  conclude/  reconcile/
  digests/               content-hash digests (see Tokens)
  • Stays outside: host-owned config (.claude/, .agents/, .opencode/), .secrets/, and the human-facing deliverables a plan writes into docs/implementation/<x>/. Those are project documents and keep their current home. Say if you would rather have those under .do-it/ too.
  • Mechanism: every stage plugin resolves its root from DO_IT_HOME, defaulting to <repo>/.do-it. The same default applies when a plugin runs standalone, so there is one layout, not two.
  • Migration: do-it doctor --migrate moves legacy folders when no run is in flight. In-flight runs stay on the legacy path until they finish, and the plugins read the legacy path as a fallback for resume.
  • Git: one ignore line for .do-it/. A decision that must outlive the clone belongs in the project docs, not here.
  • Open: with git worktrees (Engine uses .wt/), is there one .do-it/ in the main checkout or one per worktree? engine-deploy already writes its run log in the main checkout. Recommend the main checkout, resolved through git rev-parse --git-common-dir.

The Engine layer: a spec we hand over, not something do-it builds

do-it stays generic. For Engine it ships a written spec so Engine can later run the same lifecycle natively. The video's idea (a router plus fixed pipelines with human nodes) maps onto Engine's squad vocabulary, and the in-progress engine-dev-squad is the first real test of that mapping.

Flat squad or hierarchy of agents?

Recommendation: a flat, data-defined pipeline with one router level, and no manager-agent hierarchy. The reasons come from Engine's own constraints, not from taste:

  • spawn_agent is off in production, and squad steps are fenced from starting squads, so nested agents are not available at runtime.
  • Handoffs are one hop of artifact references, and a manager persona would need many more tools than the roughly 122 already used of a 128 per-turn cap.
  • Cross-repo or oversized work is already split by the PM into dependent cards. That gives a hierarchy of work without a hierarchy of agents.
  • The router (chief of staff) picks the work type, and the work type picks the step list. That is the video's factory router and Engine's existing routing table.

The one place a second level pays is the build side (orchestrator, epic builders, adversarial verifier), which is do-it's conductor-to-stage-persona model, kept one level deep and reaped.

Experiment 1

Replay five landing-page cards and three bug-fix cards through (a) a per-work-type step list as data and (b) one generic definition where a PM persona chooses the next role. Measure tokens per verified assertion, loops per card, and wrong skips (designer or QA skipped when needed). Expected: (a) wins on cost and wrong skips; (b) only on unfamiliar work types, where a manager would be added for unknown only.

Experiment 2

Take one full-stack feature and run it as two dependent cards versus one card with one dev job. Measure review rounds, rework, stale-head events and cost. If two cards is not worse by a margin, hierarchy-by-cards is the default and nested agents are never needed.

What the dev squad is, and where it already matches

A card-to-squad pipeline on Control Tower: chief of staff, PM, designer (new UI only), dev, reviewer, QA, merge, docs round. Control flow lives in a code statechart of about 35 states. The plan is 26 epics and 549 test cases (95 tagged live-tenant). Wave 2 closed on 2026-10-10 and wave 3 is next. The real board is delivery/STATUS.md; the top-level STATUS.md is stale.

It already matches do-it on tiers, the review cap of two, and the four-term status vocabulary, including IMPLEMENTED-NOT-VERIFIED. It is ahead of do-it in places, so do-it should copy it:

  • Per-case test contract with a live-system tag. A live-tenant case that cannot be reached stays IMPLEMENTED-NOT-VERIFIED and never goes green. DoD rows in do-it should carry the same tag and rule.
  • Head-commit binding. A review or QA verdict is bound to the commit it saw, and a moved head makes it stale. The do-it verifier should do the same.
  • Default-accept-by-ID owner questions, which cut your reply to the exceptions.
  • Frozen contract with an amendment log. Squads file amendments and the orchestrator folds them in, which removes parallel-writer conflicts. Useful for multi-lane builds.
  • Collision board with gate and deploy slots, and an untrusted-input boundary (text from outside never picks tools or repos, and a persona holds no write token).
  • Kickoff files as resume prompts that pin the main-branch commit and stop on a mismatch.

  14. Conformance suite: replay one wave-3 landing-page card as the acceptance test, plus negative cases (stale head, budget denied, loop cap, injection).
  15. What Engine must provide natively, what stays optional, version rules.

Decomposition: split so the big model touches few tokens

Illustrative shape of a bug-fix stage. The point is who reads what, not the token counts, which are not measured here.

collect logs, git state, failing test→cheap: digest to ≤2K tokens→top: diagnose from the digest only→mid: implement against the test→gates→cheap: write report

Split when

A slice has a deterministic part, a read-heavy part, or a decision part that can be separated by a file. The top tier then reads a digest, not the repository.

Do not split when

The saving is smaller than the spawn cost. Each fresh worker pays its brief and a cold start (workers in the founding case began near 57K tokens of context). A one-file change runs inline, as engine-deploy already says.

Write-side rule

Splitting applies to reading and thinking. Writing stays single-threaded per area, because parallel writers produce incompatible work (Cognition, Apr 2026).

Rules do-it codifies (13, each from a cited source)

  1. Stable prefix, volatile tail. Static instructions and tools first. No timestamps, run IDs or git status in the system block or early blocks.
  2. Append-only history. Never edit, reorder or summarize earlier messages in place. Compaction only as a fork that reuses the parent prefix.
  3. Deterministic serialization. Tools sorted by name, stable JSON key order, stable order for MCP tools. (A Codex fix for hash-map tool order is the cautionary tale.)
  4. Never add or remove tools mid-session. Restrict through state messages or deferred stubs.
  5. Never switch model mid-session. Hand off through a fresh subagent with a written brief. This agrees with the routing rule above.
  6. Updates go in the next message, not the system prompt: time, changed files, finish-line board.
  7. Do not change thinking or effort level, tool choice, images or speed mid-thread.
  8. Put the cache breakpoint on the last byte-identical block.
  9. Warm, then fan out. Send one request, wait for its first response, then start sibling workers on the same prefix. Starting them all at once means none finds a cache entry.
  10. Pick the TTL by the expected gap. When the gap between calls exceeds five minutes, the one-hour option pays back after two reads on Anthropic's published multipliers.
  11. Prefer fewer, larger prefix-sharing workers. A prefix below the provider's minimum (512 to 4096 tokens, by model) does not cache, so do not pay a write premium there.
  12. Measure every call. Hit rate = read ÷ (read + write + uncached). Alert on drops; ignore sessions under about 20 requests.
  13. Send a session affinity key on every route that supports one.

What do-it adds itself, and only that

do-it cannot inject into a harness's prefix when it delegates to Claude Code, Codex or opencode. The prior-art pass found no existing project that covers these, so they are the build list:

  1. Cache-safe handoff across harnesses: a fresh subagent with a short stable preamble plus a tail brief, so each spawn starts with a prefix the host can cache.
  2. One cache telemetry format across hosts. ccusage covers Claude Code and Codex logs and LiteLLM covers API calls, but nothing unifies them with opencode, DeepSeek and Engine.
  3. A cost-aware policy: when to pay for the longer window, when to keep a worker warm or restart it, when a model switch beats staying. No project publishes one (absence of evidence, not proof).
  4. Fan-out warming across mixed providers, each in its own provider's way.
  5. Cache-safe compaction on non-Claude drivers. The fork pattern is specific to Claude Code.
  6. A prefix diff detector that names the block that busted the cache. Anthropic mentions a cache diagnostics feature; check it before building this.

Published hit rates (about 92% for Claude Code and 89% for opencode in one secondary dataset) are not a baseline. do-it measures its own.

Local mechanics that sit on top

  • Digests keyed by content hash. A file read once becomes .do-it/digests/<sha>.md (built with a deterministic packer such as repomix where it fits). Later briefs cite it, and a changed file gets a new key.
  • The resume prompt is a fixed template built from state files, so it caches too.
  • Wake rules follow the cache window. Waking a large context after expiry pays a full write, so reset first (01, SL-3).
  • Keep the always-loaded surface small. Stage skills load on demand and the tool list is identical across spawns.

Each stage plugin writes one atomic result.json as its last act. This is the smallest change that unlocks everything else.

Stage-specific fields extend it: plan-it adds tallies, waves and DoD rows; build-it adds per-row VERIFIED / IMPLEMENTED-NOT-VERIFIED / BLOCKED with an evidence reference and a run verdict (DONE_ALL_VERIFIED, DONE_WITH_RESIDUALS, BLOCKED, NEEDS_RESET, USAGE_LIMIT); deploy-it adds its leg list. deploy-it adapter, so the Engine specifics move out of the plugin

Executable-first, so any host can drive it: a .deploy-it/adapter.json manifest plus commands that already speak the LEG protocol engine-deploy.sh uses. Required leg ids are fixed, and the result states are DEPLOYED_VERIFIED, DEPLOYED_UNVERIFIED, HELD, FAILED, NEEDS_HUMAN. The Engine adapter keeps the tenants box, ghcr registry, terraform digest pin, the three-deployment rule and the seam-contract probe. A Vercel or plain-Docker adapter would be a second, small file.

107 cards: how many sandboxes, how many tasks

Sandboxes
Not 107. Boxes follow slices and roles, not cards. Discovery is read-only and handles many cards per worker. Only cards that turn out to need a build become slices. How many that is stays unknown until discovery runs; I will not guess a number.
Engine tasks
One parent card for the drain. Each card needing a build becomes a dependent child card (the PM split), each worked separately. Cards closed by verification get a disposition row on the parent and no child. If the 107 already are Control Tower cards, Engine's board is the drain and the preset shrinks to a triage card that assigns dispositions.
Cost rule
Decomposition counts spawn cost: a change that saves less than a Job start is not split. Sandbox time is billed in Engine, so this is real money there.

Cloud sandboxes: does Engine keep one open until conclude?

Not today. From the dev-squad docs: dev, reviewer, QA and docs each run as a per-task Job, work survives in the git branch and the card, and the only warm box is the preview (2 h idle teardown). Running do-it local is easy; in the cloud do-it's requirement is only that any step can start cold from a git ref plus the previous result file. A warm lease per card, killed at conclude or on an idle timeout, is an optimization that Engine can add; it should be chosen after measuring Job start, clone and install time, which the docs do not give. That is the Engine layer's call, recorded in the spec (03-ENGINE-LAYER-SPEC.md).

When the conductor passes its ceiling

It does not keep going and it does not silently spawn a copy of itself. At the ceiling the spine refuses the next step (a block, not a warning), writes the state and a resume prompt, and the host adapter's continue hook does what the setting says: auto starts a fresh conductor from those files, ask prints the one-line command, off parks the run. Auto handoffs are capped per run (default 5) and each is logged; after the cap the run parks and the report says why. In Claude Code the old session cannot clear itself, so auto means a new headless process; I have not tested that with your subscription aliases, so it is a checklist item. In Engine there is nothing to hand off, because the next step is a new Job anyway.

The pack is one canonical file (owner-pack.json: numbered questions, each with a recommendation, options and a default). A renderer shows it, and the answer comes back as a terse reply (1 yes 2 no 3: use B) that do-it answer parses. Each host adapter implements the same two calls: render(pack) and collect() → answers. Credentials: asked once at first run

do-it init asks where credentials come from: a file (your .secrets/ folder, gitignored), an environment variable, AWS Secrets Manager, or 1Password. It stores a reference, never a value. Values go only into the environment of the subprocess that needs them and never into events, briefs, the owner pack or the model context. A missing credential is a blocker found at plan time by a live preflight, not a question in the middle of a build. The AWS and 1Password providers need your own CLI sessions; cloud hosts use their own secret store.

Observability: Langfuse and LangSmith go to v2

A real exporter needs a client per vendor, offline buffering and prompt redaction, which breaks the single-file spine. v1 does the cheap half: events.jsonl and token-meter.jsonl freeze the fields a trace needs (run, slice, stage, persona, tier, model, tokens, cache read/write, estimated flag, verdict, parent). v2 then reads those files. The .env.example with LANGFUSE_ENABLE=false and a provider switch is drafted in docs/implementation/do-it-v2/README.md, names only, values resolved through the secrets provider. I did not verify either vendor's current ingestion API.

parallel-lifecycle: keep it a separate plugin

Do not merge it into build-it or do-it. It provisions a per-worktree app port, headless Chrome and database through Claude Code hooks, and review-it already reads its .env.worktree contract; folding it in would drag Claude-specific hooks into the generic core. The clean seam is an isolation driver in settings: worktree (parallel-lifecycle), job (Engine), none. do-it declares it as a soft dependency and owns only the scheduling of which slice goes in which isolation. Whether Claude Code plugins can declare plugin dependencies is still unverified; the fallback is do-it doctor --install.

Repo layout and host adapters
