## 2. Attacks on the round-9 fix

- **Can "skip while an open stop-gate question exists" suppress a park?** No. The rule only holds back the question; the park goes ahead. I ran a park (Q1), then `resume` with Q1 unanswered, then reached patience again: hook 2,0 and PARKED. The second `stop_parked` event names Q1. Q1's text lists the first park's rows, so it can be stale if the rows changed (L-d). After `pack withdraw` and a resume, the next park adds Q2.
- **Can a non-gate question that looks like one block parking?** No.
  - `" The run stopped…"` (leading space) and `"…with 01 open row(s)…"` → `STOP_GATE_TEXT_RESERVED`.
  - A lowercase `"the run stopped…"` is recorded as a stage question. Because the gate matches the exact regex plus its own events, it is not treated as the gate's.
  - Only a hand-forged `stop_parked` event works (L-e).
- **`pack withdraw`** works: `PACK_WITHDRAWN` for n=1, and the next park asks n=2.
- **I/O fault between the pack write and the state write** (`chflags uchg state.json` at patience): hook 2 ×4, the run is not parked, 1 open stop-gate question, and no `stop_parked` event. The dedupe holds at 1. After `nouchg` the run parks and reuses that question. See L-f.
- **Garbled `answers.json`** after a park and resume: `packAppend`'s new open-question check throws, which becomes `parkError`. Refusals are counted (4 at patience 1), the run never parks, and the hook exits 2 every time. This fails closed. See L-g.
- **Slowness:** a 248 MB `events.jsonl` of `stop_parked` lines at patience parks normally in 3.4 s, well under the hook's 20 s spine timeout. The new event scan opens no allow by timeout.

## 4. New findings

### R10-S1-M17 MEDIUM: a second park with the same open rows, after the owner answered the first park question, adds no question, so the run is parked and waiting on nobody

```
patience 1; gate advance → BUILDING
hook 2, hook 0                      → PARKED, owner-pack Q1 (the gate's park question)
answer --reply "1: resume run"      → ANSWERED
resume                              → RESUMED, BUILDING
(no progress) hook 2, hook 0        → PARKED again
owner-pack: [Q1 answered]; stop_parked events: question 1, then question null
```

How it happens:
- `packAppend` (`pack.mjs:29`, bundle `:1806`) skips any question whose text matches a row that is not withdrawn. That includes a question that has already been **answered**.
- With the same open rows and the same patience, the park text is identical, so the second park adds nothing.
- The new `{ stopGate }` skip does not help, because an answered question is not open.
- Then `refuseOrPark:128-131` finds no open question, so the `stop_parked` event carries no question number.

Result: the run is PARKED, which does not gate, while the owner pack shows nothing to answer. The owner is never asked about the second park. That breaks "at patience the run is parked with one owner-pack question" (`stopgate.mjs:84`) and the fix's claim that "once the gate question is answered, the next park asks again". The r9 unit test only shows that claim with a different row list.

The same thing happens when the owner answers a dangling question (L-f) before the park actually happens. Answering "close with residuals" on a BUILDING run changed nothing, and the later park then asked nothing.

Grading:
- **MEDIUM (wrong state).** It is not a G-1 false pass: the park itself is legitimate at patience.
- **Origin:** pre-existing. The text dedupe is ruling D7 and is the same at v1.0.5 (`x.text === q.text`, no status check) and at 3160029.
- **Hand-made artefact:** none, it happens in normal use. **Exotic host:** no.

Fix: for the gate's own question (`opts.stopGate`), dedupe only against **open** questions (not withdrawn and not answered), for example `openOf(...)`, rather than against every non-withdrawn row. Regression test: park, answer "resume run", resume, park again with the same rows. Assert one new open stop-gate question, and that the second `stop_parked` event names it.

### LOW

- **L-d (stale text, new 1.1 surface from f03db4e).** A re-park while an older gate question is still open (a resume without answering) reuses the old question. Its text names the open rows of the first park. The park is correct; only the wording can be stale.
- **L-e (needs a forged `events.jsonl` line).** A hand-written `stop_parked` event with `{question: n}` that points at a stage question has two effects: the gate parks without adding its own question (the skip rule), and `pack withdraw --by stop-gate` withdraws that stage question. The withdraw half is pre-existing (R5-S1-H10 trusts events). The skip half is new. Not a false pass.
- **L-f (residual of R9-M16 for I/O faults; needs `chflags uchg` or a disk filling between two writes in one folder).** `stateBytes` test-serialises only schema and cap. When `writeState` then fails on I/O after `packAppend` succeeded, 1 open park question is left for a run that is not parked. It is bounded at 1, and the next writable stop parks and reuses it. CHANGELOG ("a park that cannot be written adds nothing to the owner pack") overclaims for this case. Fix: withdraw the just-added question in the park branch's `uncounted` path (r9 fix option a), or narrow the CHANGELOG wording.
- **L-g (fail-closed trap, new 1.1 surface; needs a hand-garbled `answers.json`).** The new open-question check in `packAppend` reads `answers.json`, so a garbled `answers.json` makes every park fail. Refusals then count past patience and the run never parks. The refusal holds, so this is the same class as L-a.
- **L-b residual (documented in 97c02b0; needs a hand `chmod` plus a hook with no session id).** A run started without `--session` (cwd-owned) inside a 0311 `runs` folder: the hook with no session_id → 0 with a `runs_unlistable` note. When the folder is listable, the same hook → 2.
- L-a and L-c from r9 are unchanged and now documented (CHANGELOG, SKILL step 7, README).
