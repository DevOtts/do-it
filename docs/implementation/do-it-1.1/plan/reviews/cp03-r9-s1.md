## 3. New findings

### R9-S1-M16 MEDIUM: at patience with a failing state write, every stop appends another stop-gate question to the owner pack, and the run is never parked

```
plan [{id:"aaaaaa"},{id:"s1",depends_on:"aaaaaa"×600000}]  → gate build READINESS_OK
patience 1; hook → 2 (stop_refusals 1, counted)
.secrets/<"K"×40> = "aaaaaa"                                → every state write is now STATE_TOO_LARGE
6 stops: hook 2 each; owner-pack.json questions: 1, 2, 3, 4, 5, 6
state: BUILDING, stop_refusals 1 (never PARKED)
```

How it happens:
- In `refuseOrPark` (`stopgate.mjs:91-102`), `packAppend` runs **before** `writeState`. That ordering comes from R7-S1-L5, so that a pack that cannot be written never parks the run.
- When the pack write succeeds and the state write then fails, `uncounted()` returns. The question stays in the pack, but the state, still at `stop_refusals >= patience`, is not changed. So the next stop takes the same branch again.
- `packAppend` dedupes on `x.text === q.text` (`pack.mjs:24`), but the stored text has already been redacted by `atomicWriteJson`, and here it contains a `[REDACTED:…]` row id. So the compare never matches, and each stop adds question n+1. The growth has no bound until the pack itself reaches the cap.
- Without redaction, the dedupe holds. Even then, one open "Resume the run or close it with residuals?" question is left for a run that is not PARKED, which is wrong state.

Grading:
- **MEDIUM (wrong state).** The owner pack holds N identical open park questions for a run the gate never parked. The owner is asked to decide on a park that did not happen. The refusal itself still holds, so this is not a G-1 false pass.
- **Origin:** a 1.1 regression surfaced by 0346e00. Before 0346e00 the same branch allowed the stop and also left the question, so it is pre-existing in the 1.1 ordering, but the refuse-forever loop now makes it repeat on every stop.
- **Hand-made artefact:** same as R8-P3. It needs an agent-written plan plus `.secrets/<name>`, and a stored count at patience: either refusals that reached patience before the write broke, or a patience lowered in the agent-writable `settings.json`. **Exotic host:** no.

Fix (any one closes it):
- (a) In the uncounted path of the park branch, withdraw the question `packAppend` just added.
- (b) Dedupe in `packAppend` against the redacted form of `q.text`, and also skip the append when an open `source:"stop-gate"` question already exists for the run.
- (c) In the park branch, test-serialise the state (the `jsonBytes` cap check) before appending.

Regression test: the P3 setup at patience 1 with one counted refusal, then N stops. The test should assert that the pack has at most 1 stop-gate question (or 0) and that the hook still exits 2.

### LOW

- **L-a (documented limit, new 1.1 surface).** An uncounted refusal never parks, so an unattended session loops on refused stops until the write fault (ENOSPC, EACCES, cap) is fixed. This is the deliberate CONTRACT §3.1 choice, and it is documented in CHANGELOG.md:11. It sits in tension with X27, but it is not a false pass, and each refusal prints the cause.
- **L-b (fail-open misreport, origin likely pre-existing, needs a hand `chmod`).** With `.do-it/runs` at mode 0311 (it can be traversed but not listed), the hook exits 0 with nothing on stderr, and `gate stop` → `STOP_ALLOWED` "no run is owned by this session or cwd". The run's `state.json` is readable by path, and the session registry names it. It falls within the §3.1 "cannot read the state" fail-open in spirit, but the reason is wrong and no `stop_gate_state_unreadable` event is logged. Suggestion: when the runs folder cannot be listed, fall back to the registry's run ids for the cwd home, or at least report `state unreadable` with the error.
- **L-c (note, documented R4-S1-M7).** When the registry path is a file at `start`, the run gates only from its own cwd: the hook from another cwd → 0, silently.
