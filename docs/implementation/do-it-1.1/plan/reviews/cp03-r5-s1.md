## 2. New findings

### R5-S1-H9 HIGH: a deploy-legs result takes any run to FAILED with no reason and no evidence, so the stop is allowed. `gate escalate` then makes the run terminal

```
A=start --preset feature --session dpi-s; next --run A                                   # INTAKE, 10 OPEN rows
results/r.json = {"schema":"it-result/1","stage":"build-it","run_id":A,"slice_id":null,
                  "status":"ok","exit_code":0,"verdicts":[],"legs":[{"leg":"web","state":"FAILED"}]}
record --run A --result results/r.json → {"outcome":"DEPLOY_FAILED","status":"FAILED"}    # from INTAKE
status → FAILED, no status_reason ; hook dpi-s → exit 0                                    # board 0 of 10 closed
gate escalate --run A --reason "deploy broke" → ESCALATED (pack_question 1) ; hook → 0 ; registry entry pruned
same from BUILDING with "status":"failed" and no reason → DEPLOY_FAILED, FAILED, hook exit 0
on do-it 1.0.5 (d38cedb), the same result → DEPLOY_FAILED, and then gate stop → STOP_REFUSED
```

This got through with one agent-written result file and no hand edit.
- The R4-S1-H8 fix (`FAIL_REASON_REQUIRED`) sits only in the non-deploy `else` branch of `planRecord`.
- When `result.legs` is non-empty, `planDeploy` (legs.mjs) sets `runStatus = 'FAILED'` whenever any leg says FAILED. That holds whatever `result.status` says (here `ok`), whatever the run's status is (here INTAKE, never DEPLOYING), and when the leg has no evidence.
- FAILED is non-gating in §3.1, so the hook allows the stop.
- Nothing downstream flags a FAILED run that has no `status_reason`. `NON_GATING_OWNERS.FAILED` says "record (a failed result with a reason)", and this path breaks that.

Origin: **1.1 regression**.
- `legs.mjs` is unchanged since d38cedb, but in 1.0.5 the stop gate never looked at status, so a FAILED run with open rows was still refused (shown above).
- 1.1 made FAILED non-gating (02c6f53) and left this path in.
- The R4-S1-H8 fix (7b38a7b) did not cover it.

Fix:
- `record` refuses a deploy-legs result unless the run is in DEPLOYING, PROVING, PARTIAL_FAILURE or ROLLED_BACK (the statuses that have legs). Use `DEPLOY_OUT_OF_ORDER`.
- A leg that is FAILED or NEEDS_HUMAN needs non-empty `evidence` or a `reason`. Store it as `status_reason`, the same as the run-level `failed` case.
- Regression test: run the two results above from INTAKE and from BUILDING. Each must be refused, the status must stay put, and the hook must exit 2.

### R5-S1-H10 HIGH: a needs_human question tagged `source: "stop-gate"` can be withdrawn with `pack withdraw --by stop-gate`. The run is then left NEEDS_HUMAN with no open owner-pack question, and the stop is allowed

```
A=start --session wd2-s; next --run A; gate advance --run A --to BUILDING                # 10 OPEN rows
q.json = [{"text":"Which region should prod use?","kind":"owner-gate","source":"stop-gate",
           "options":["eu","us"],"recommendation":"eu","default":"eu"}]
record (status needs_human, pending_human.questions_path q.json) → RECORDED, NEEDS_HUMAN
pack withdraw --by stop-gate --run A → PACK_WITHDRAWN                                    # 0 open questions
status → NEEDS_HUMAN ; next → NONE reason needs_human ; hook → exit 0
gate escalate --run A --reason "a b c" → TRANSITION_REFUSED "no open owner-pack question"
variant without the source field: text "The run stopped with 1 open row(s) after 3 refusals: …",
  kind default, from INTAKE → withdrawn by the text-template fallback, same end state
```

This got through with one result file and one documented command, and no hand edit.
- The R4-S1-H8 fix is supposed to guarantee that a run enters NEEDS_HUMAN only when a question lands open in the owner pack. It checks this only when the result is recorded.
- `packAppend` copies a result's own `source` field through, and `isStopGateQuestion` trusts it, or a text that matches the template.
- So the agent can label its own question as a stop-gate question and withdraw it.
- The run then waits on nobody. The owner pack shows nothing open, `escalate` refuses, and the hook allows every stop for good.
- The only thing left behind is the withdrawn entry in `owner-pack.json` and a `pack_withdrawn` event. No check reads either of them.

Origin: **new 1.1 surface**. The `source` field, `isStopGateQuestion` and `pack withdraw` came in with 02c6f53, and the NEEDS_HUMAN invariant came with 7b38a7b.

Fix:
- `record` drops any caller-supplied `source` from result questions, since only spine-internal callers may set it.
- `record` refuses a question text that matches the stop-gate template.
- `isStopGateQuestion` uses its text fallback only for packs written before `source` existed (no question in the pack has a `source`).
- `pack withdraw` refuses, or puts the run back to its previous gating status, when the withdrawal would leave a NEEDS_HUMAN run with no open question.
- Regression test: run the commands above. The withdraw must be a no-op or the status must be restored, and the hook must exit 2.

### R5-S1-M9 MEDIUM: an error writing to one run in the cwd's home is thrown out of the whole gate. It opens the stop for the other runs of that home and for every other registered home

```
two homes, one session: A open in X, B open in Y. chmod 555 X/.do-it/runs/<A>
hook xo-s from X      → exit 0 ; gate stop → INTERNAL_ERROR "EACCES … runs/<A>/.state.json.tmp-…"
hook xo-s from parent → exit 2                                   # Y's B is refused when X is not the cwd
same home: A1 (older, open), A2 (newer, open), chmod 555 runs/<A2>
hook sh-s → exit 0 ; gate stop → INTERNAL_ERROR                  # A1 valid and open, not gated
```

- In `gateStop`, an error from an extra home is caught and goes into `unreadable_homes`. An error from the cwd's home is rethrown (`if (h.own) throw`).
- Inside `hookStopIn`, `refuseOrPark` (`writeState`) and `loadState` errors other than TAMPERED or INVALID are not caught per run.
- So one run that cannot be written hides every other run, in its home and in other homes.
- That is the S1-M1 class (one bad run hides a valid one), here through a write error. It is also the R4-S1-M7 class turned around: the fix made sure a bad other home cannot open the cwd's gate, but a bad cwd home still opens the other homes' gates.
- Against §3.1: the only fail-open rule is "state.json unreadable" for that run. A write failure in run A is not a reason to allow the stop for run A1 or for run B.
- The fix report's open note calls this "the documented 'broken spine must not trap the session' rule". But the spine is not broken here, since B and A1 are evaluated fine as soon as the error is contained.

Origin:
- The single-run, single-home case is **pre-existing 1.0.x**. On d38cedb the same chmod gives INTERNAL_ERROR.
- Hiding other runs and other homes is a **new 1.1 surface**: the multi-run gate from the R2-S1-H4 fix, and `if (h.own) throw` from 8735ec6.

Fix:
- Evaluate each run inside its own try. A run that throws is reported (`unwritable: [{run_id, error}]`), fails open for itself alone, and is logged where possible.
- In `gateStop`, an error in the own home is treated like an error in another home: report it and keep the other homes' answers. Throw only when every home failed.
- Regression test: run both cases above. The hook must exit 2.

### R5-S1-M10 MEDIUM: a FIFO (or a symlink to `/dev/zero` or another endless file) in the session registry hangs the spine. The hook times out after 20 s and fails open for every home, the cwd's own included

```
A=start --session ff-1 in X; next; progress; hook ff-1 X → exit 2
mkfifo $DO_IT_USER_HOME/sessions/ff-1/zz-evil.json
progress; hook ff-1 X → exit 0 after 20s     # callSpine timeout → json null → exit 0; the spine process is left blocked
rm the fifo → hook → exit 2
```

- `readEntries` reads every `*.json` in the session folder with `readFileSync`, and so does `liveEntry` for `<home>/runs/<id>/state.json` from a forged entry. A FIFO blocks that read forever.
- The hook's `spawnSync` timeout (20 s) then returns no JSON, and the hook maps that to exit 0.
- The R4-S1-M7 fix claims that a broken registry never opens the cwd run's gate, and this breaks that claim. It needs a hand-made file in the registry, as the garbled-registry case of R4-S1-M7 did, so it is graded MEDIUM on the same standard.
- Ordinary forged entries were contained. A run_id of `../../../../etc`, a home of `/nonexistent`, and a symlink to `/etc/passwd` were each pruned or reported, and the hook exited 2. The symlink's error text quotes the first bytes of the target (`"##\n# User "…`), which is a small leak.

Origin: **new 1.1 surface** (session registry, 594da8e and 0e688a2).

Fix:
- Before reading a registry file or an entry's state.json, `lstat` it. Skip and report anything that is not a regular file, and cap the read size.
- Do not quote file contents in `registry_unreadable`.
- In the hook, a timeout while the cwd's home has an owned gating run should not be read as an allow. At least log it, or let the spine run its own deadline so that it answers with what it has.

### R5-S1-M11 MEDIUM: a stop whose cwd no longer exists, or cannot be entered, is allowed. The spine would have refused it

```
A=start --session ce-1 in X; next; progress
hook ce-1 <parent>/gone           → exit 0       # cwd deleted (e.g. a removed worktree)
gate stop --session ce-1 --cwd <parent>/gone (run from elsewhere) → STOP_REFUSED
hook ce-1 <dir at chmod 000>      → exit 0
```

- `callSpine(args, cwd)` spawns the spine with `cwd: input.cwd`. When that directory is gone or cannot be entered, `spawnSync` fails, stdout is empty, `json` is null, and the hook exits 0.
- The spine itself handles a missing `--cwd` and finds the run through the registry, which is what the R3-S1-H7 fix promised ("the stop gate finds a session's runs from any cwd").
- This needs no hand edit. Removing the worktree the session is standing in is ordinary in multi-worktree runs like this release.
- It is graded MEDIUM, not HIGH, on the R4-S1-M8 precedent (no hand edit, but a rare precondition). Claude Code usually resets a vanished cwd, so how often the host sends one is unproven.

Origin: **new 1.1 surface**. The spawn line is the same at d38cedb, but in 1.0.x the gate was cwd-only, so a missing cwd found no run anyway.

Fix:
- Spawn the spine from a directory that is sure to exist (the hook's own dir or `os.tmpdir()`) and pass the host cwd only as `--cwd`.
- Regression test: run the two hook calls above. Both must exit 2.

### R5-S1-M12 MEDIUM: two session ids that differ only in letter case share one registry folder. One session's stop deletes the other session's entries, and the other session's stop from another folder is then allowed

```
(macOS default, case-insensitive)
A=start --session case-sess in X; next; progress; hook case-sess <parent> → exit 2
hook CASE-SESS <parent> → exit 0 ; sessions/case-sess/ is now empty         # liveEntry: owner ≠ CASE-SESS → pruned
progress; hook case-sess <parent> → exit 0 ; hook case-sess X → exit 2
```

- R4-L5 was left open as "share a registry folder". It is worse than that: `sessionHomes` prunes any entry whose run "now belongs to another session", so the case twin deletes the real owner's files.
- I have graded it MEDIUM because the owner's stop from a sibling folder is then a false pass with no hand edit. It is still unlikely on the shipped host, whose ids are lowercase UUIDs. `DO_IT_SESSION_ID` and `--session` accept any id, though. The lead may grade it LOW as a documented limit.

Origin: **new 1.1 surface** (0e688a2, and R4-L5).

Fix:
- Fold case in `safeName`, or always use the digest form for the folder name.
- Prune only entries whose stored `session_id` equals the reader's session id, compared exactly.

### LOW

- **R5-S1-L1, new 1.1 surface (7b38a7b).** A run-level `blocked` reason of `.`, `x`, `n/a`, `TODO`, `-` or a zero-width space (`​`, which `trim()` keeps) is accepted, and the run goes to BLOCKED with the hook allowing the stop. A non-breaking space alone is refused. The contract asks for a reason, not a good one, and the reason is stored and shown, so this is a contract choice. A minimum (for example 3 distinct words, as A1-M2 required for evidence) and a `\p{White_Space}`/`​` strip would close it cheaply.
- **R5-S1-L2, pre-existing 1.0.x.** A board that parses but has the wrong shape (`{}`, `{"rows":null}`, `{"rows":{}}`, `null`, `[]`) is read as `{rows: []}`, so the result is `STOP_ALLOWED "no open rows for this run"`. Only a parse error fails closed (A16). That makes A16 inconsistent, and it needs a hand edit of `.do-it`. Fix: in the hook path, `readFinishLine` treats a non-array `rows` the way it treats a parse error.
- **R5-S1-L3, pre-existing 1.0.x (redactText in atomicWrite at d38cedb).** The R4-L4 protocol words cover statuses and outcomes, but not JSON keys. Here is what happens with `.secrets/k` set to `session_id`, `run_id` or `evidence`:
  - The first refusal writes `state.json` through `redactText`, so its keys become `[REDACTED:k]`.
  - The next stops are `0,0`.
  - This needs a planted secret, the same class as R4-L4.
  - Fix: redact values only, never keys, in spine-owned JSON. Better still, never text-substitute `state.json` or `finish-line.json`, and redact only their free-text fields.
- **R5-S1-L4, pre-existing 1.0.x.** With a garbled board, the run is refused up to patience and then parks with the question "… 1 open row(s) … finish-line.json unreadable". After `resume`, `next` → `INTERNAL_ERROR`, because `next` does not report the unreadable board. Parking here is §3.1 and A16 as written, and it holds. The follow-up message is just poor.
- **R5-S1-L5, new 1.1 surface.** `registry_unreadable` error text quotes the target file's first bytes. See R5-S1-M10.

Also held:
- Questions taken from another run's `owner-pack.json` (`questions_path` → `.do-it/runs/<B>/owner-pack.json`) land only in the recording run's own pack. Each pack has 1 question, and B's pack is untouched.
- A session id of `../../evil`, `a/b` or `....` is stored by digest (`h-…`), and nothing is written outside `sessions/`.
- The garbled-board path does not open the stop early. It parks only at patience, and other homes stay gated.
