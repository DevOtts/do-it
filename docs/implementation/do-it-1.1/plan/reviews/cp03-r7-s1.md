## 2. New findings

### R7-S1-M14 MEDIUM: `gate build` writes a `state.json` larger than the spine's own 16 MiB read cap. The run is then "state unreadable" for good, and every stop is allowed with every row open

```
A=start --preset feature --session big ; next --run A                     # INTAKE, 10 OPEN rows, patience 50
.do-it/plan/READINESS.json = {"decisions":[],"preflight":{"passed":true},"credentials":[],
                              "slices":[{"id":"s0"} … {"id":"s79999"}]}     # 2,708,992 bytes, agent-written
gate build --run A          → READINESS_OK (12.5 s), state.json = 17,669,701 bytes
hook big X                  → exit 0, no stderr
gate stop --session big     → STOP_ALLOWED "state unreadable"              # board: 80,010 rows, all OPEN
status --run A              → INTERNAL_ERROR "larger than 16777216 bytes: …/state.json"

two-slice variant: slices [{"id":"s0"},{"id":"s1","depends_on":["s0" × 1,300,000]}]
  READINESS 6,500,111 bytes (compact) → READINESS_OK, state.json 18,201,251 bytes → hook 0, "state unreadable"
```

- `writeState` (`state.mjs:44`) validates the schema and writes `jsonBytes(state)`, which is pretty-printed. Nothing compares the size with `STATE_READ_CAP`.
- Every reader of the state (`loadState`, `listRunIds`, `selectScopedRunId`, the registry check) is capped at 16 MiB since 14fe5f5 (R5-S1-M10) and 41e803f (R6-S1-M13).
- `seedSlices` copies each slice's `id`, `lane`, `tier`, `wave` and `depends_on` into state. None of them has a length limit in `readiness.schema.json`. The pretty-printing makes state about 2.8 to 6.5 times larger than a compact `READINESS.json`. So a READINESS well under its own 16 MiB cap yields a state above it.
- From then on the spine cannot load the run, so every command on it fails (`status` gives INTERNAL_ERROR). The stop gate takes the §3.1 "state unreadable" branch and allows every stop, silently, for as long as the run exists.
- Against §3.1, the fail-open rule exists for a state that broke. Here the spine itself writes a state it refuses to read, and that turns a well-formed plan into an open gate.
- **Downstream detection:** partial. A `stop_gate_state_unreadable` event is logged, `status` errors, and the run can never reach DONE. But the session is free to stop with all rows open, which is the exact false pass G-1 exists to prevent.
- **Origin:** **1.1 regression.** At d38cedb, `loadState` read with an uncapped `fs.readFileSync`, so the same plan was still gated. The cap came with 14fe5f5 and was extended in 41e803f.
- **Hand-made artefact:** no hand edit of a spine file. It needs an agent-written `READINESS.json` that is absurdly large (80,000 slices, or 1.3 M duplicate dependencies). That is the same precondition as R6-S1-L2, but here the result is a false pass rather than a large refusal, so I grade it MEDIUM, not LOW. **Exotic host:** no.

Fix:
- `writeState` measures `bytes.length` before it writes anything. Above `STATE_READ_CAP` it throws `STATE_TOO_LARGE` and leaves the previous state in place. Then `gate build` fails, and the run stays INTAKE and gated.
- `checkReadiness` also refuses a plan whose seeded slices would exceed a budget, for example a cap on the slice count, on `depends_on` length and on string lengths in `readiness.schema.json`. Such a plan is `READINESS_INVALID`, so the error names the plan, not the state.
- Optional: write state as compact JSON. That makes it 2 to 3 times smaller, but it does not remove the need for the write-side check.
- Regression test: the 80,000-slice and the two-slice plans → `gate build` is refused, `state.json` stays readable, and the hook exits 2.

### LOW

- **R7-S1-L5: an `events.jsonl` that is not a regular file opens the stop for its own run, and nothing says so. Contract choice, new 1.1 surface (41e803f with eachRefusal).**
  - Setup: one run in one home, with its `events.jsonl` replaced by a FIFO, a device link, a directory, a symlink loop or a symlink to a FIFO.
  - Result: `STOP_ALLOWED` "the refusal could not be written for any run with open rows", with `unwritable` in the JSON. The hook exits 0 and prints nothing on stderr. `status` reports nothing.
  - `refuseOrPark` has already written the state with the higher `stop_refusals` before `appendEvent` throws. So the refusal could have stood without its log line.
  - The same thing happens in a single home when `owner-pack.json` is a FIFO at the park step (patience reached): the run stays INTAKE and is allowed.
  - This is what the R6 reviewer proposed ("fails open for its own run only"), and the regression test asserts it. But §3.1 names only "state.json unreadable" as a fail-open reason.
  - Suggest:
    1. When the state write succeeded and only the event append failed, refuse anyway.
    2. When a park cannot be written, refuse rather than allow.
    3. Make the hook print the `unwritable` list on stderr whenever it allows a stop.
  - Needs a hand-made FIFO in `.do-it/`.
- **R7-S1-L6: the lint does not cover `core/drivers/secrets/file.mjs`, which is bundled and reads with a raw `fs.readFileSync`. Pre-existing 1.0.x.**
  - Setup: `READINESS.json` names the credential `API_KEY`, and `.secrets/API_KEY` is a FIFO.
  - `gate build` hangs until killed (my 15 s timeout gave ETIMEDOUT), and the run stays INTAKE.
  - The stop gate is not affected: the hook still exits 2 in 0.4 s. `redactInit` reads `.secrets/*` safely.
  - So this is a hang with no false pass.
  - Fix:
    1. Route the driver through `readRegularFile`. `core/drivers` may import `fs-atomic` in the bundle; the stand-alone module needs a local copy or a shared helper.
    2. Widen the lint to every file that `build.mjs` bundles: `src/`, `core/drivers/secrets/` and `core/renderers/`.

Notes, graded as contract or known (no new id):
- **A slice `failed` with a placeholder reason goes through the retry ladder.** From BUILDING, a slice `failed` with reason `.` (or any of the 13 forms above) → `FAILED` outcome on the first record, and ESCALATED on the second, after which the hook exits 0. This is the ladder path R6 graded as sanctioned: an owner-gate "Slice s1 failed twice" question is open. The R6-S1-L1 fix covers `blocked` but does not apply `cleanReason` to a slice `failed` reason, so the ladder's ESCALATED is reached with a placeholder cause. Same note as in round 6.
- If `state.json` is a symlink loop or dangles, or if `runs/` is replaced, the run becomes invisible ("no run is owned"). No unreadable event is logged. This is the same as deleting the run, which no gate can see.
- `readRegularFile` still has a TOCTOU window between `stat` and `open`. The `O_NONBLOCK` open plus the `fstat` re-check closes the FIFO case, so this is not exploitable for a hang.
