## 2. The write-side cap (abeb47c)

How the write paths stand:
- **State.** `atomicWrite` measures the Buffer after redaction and throws `STATE_TOO_LARGE` before it touches disk. `writeState` passes `STATE_READ_CAP`.
- **JSON files.** `atomicWriteJson` defaults to `STATE_READ_CAP`. That covers `finish-line.json`, `owner-pack.json`, the ledger, `park.json`, `wake.json`, the render record, `record.journal.json` and `install` state.
- **Answers and registry.** The answers file passes `STATE_READ_CAP`, and the registry entries pass `REGISTRY_READ_CAP`.
- **Uncapped writes.** `.state.sha256`, the init, wake-prompt and handoff text, the result copy and the migrated files are written without a cap. None of them is read back on the gate path with a cap that could fail.
- **Events.** `events.jsonl` is append-only, and the gate reads it only as best effort, in `lastEventIs`.

Probes:
- **Plan at the boundary.** I padded `s0.wave` so the seeded state lands at an exact size:
  - Exactly the cap, 16,777,216 bytes → `READINESS_OK`. The state is written, and `status` reads it (BUILDING).
  - cap−1 → `READINESS_OK`.
  - cap+3 to cap+7, ASCII or `é` (2 bytes per character) → `READINESS_INVALID`, with the run left at INTAKE and the hook exiting 2. Multibyte content is counted in bytes.
- **Large result through `record`, with the state near the cap.** `record` → `STATE_TOO_LARGE` at the journal write, which is larger than the state because it carries `next_state`. Nothing is applied: the board row stays OPEN, the state stays READY, and no journal is left. So `record` fails closed, with no partial apply.
- **Park with a pack that cannot be written.** At patience, `packAppend` failing (by FIFO, or by `STATE_TOO_LARGE` through `atomicWriteJson`) → `parkError`. The result is a plain refusal (75cda53).
- **Can a cap refusal become STATE_ERROR or "state unreadable"?** No. The spine can no longer write a state above the cap, so the "state unreadable" branch needs a hand-made state file. But a cap refusal **can** become an allow by another branch. See M15.

## 3. New findings

### R8-S1-M15 MEDIUM: the stop gate's own refusal write hits the new write cap, and `eachRefusal` turns `STATE_TOO_LARGE` into an allow. A run that `gate build` accepted is then never gated again

```
P1  plan [{id:s0}, {id:s1, depends_on: "s0" × 1,198,281}]   (agent-written READINESS.json)
    gate build          → READINESS_OK, state.json 16,777,169 bytes (cap − 47)
    status              → BUILDING, 10+ rows OPEN
    hook ×2             → exit 0, stderr "do-it stop gate: this stop is allowed because the refusal
                          could not be written for: r-… (STATE_TOO_LARGE)"
    gate stop --session → STOP_ALLOWED "the refusal could not be written for any run with open rows",
                          unwritable [{error: STATE_TOO_LARGE}]
    boundary: state at exactly the cap and at cap − 1 → same result (hook 0)

P3  plan [{id:"aaaaaa"}, {id:s1, depends_on: "aaaaaa" × 600,000}]
    gate build          → READINESS_OK, state.json 10,801,239 bytes (35 % under the cap); hook → 2
    then .secrets/<"K"×40> = "aaaaaa"     (6 chars = REDACT_MIN_LENGTH)
    status              → BUILDING
    hook                → exit 0 "(STATE_TOO_LARGE)"; gate stop → STOP_ALLOWED
```

How it happens:
- `refuseOrPark` (`stopgate.mjs:105-107`) sets `state.gates.stop_gate = { sig }` and raises `stop_refusals`, then calls `writeState`. That adds about 50 to 200 bytes.
- `planTooLarge` (`readiness.mjs:151`) accepts any seeded state of up to exactly the cap, so it leaves no headroom for the gate's own bookkeeping.
- The write throws `STATE_TOO_LARGE`. `eachRefusal` (`stopgate.mjs:46-49`) catches every throw as "unwritable", and `hookStopIn` then returns `allowed(... 'the refusal could not be written for any run with open rows')`.
- P3 widens the window. `atomicWrite` measures the bytes after redaction, and `redactInit` registers every file in `.secrets/` (6 characters or more). So a secret whose value occurs often in state values inflates the stop's write by a large factor: here each 6-character occurrence becomes `[REDACTED:` + 40 characters + `]`. The plan was checked without that secret, which no build-time check can foresee.
- No `stop_refused` event is logged, because `logEvent` runs after `writeState`. From then on every command that writes state (`record`, `next`) also fails `STATE_TOO_LARGE`, so the run can never be closed. Every stop is allowed for as long as the run exists.

Against the contract:
- §3.1 names only "state.json unreadable" as a reason to fail open. Here the state reads fine (`status` works), and the spine refuses to write its own bookkeeping.
- The R5-S1-M9 "fails open for itself alone" contract covers a run whose folder cannot be written, which is an environment fault. This is the spine's own cap applied to a plan the spine accepted. That is the M14 outcome (G-1 false pass, every row open) reached again through its own fix.

Grading:
- **Containment holds.** If the session also owns a normal run (B in repo Y), the hook from X or from Y → 2. The false pass needs every gating run of the session to be near the cap, or inflated.
- **Downstream detection: partial.** The hook prints the run and `STATE_TOO_LARGE` on stderr, and the run can never reach DONE. But the session may stop with every row open, silently as far as the events log goes.
- **Origin:** 1.1 regression. It is the incomplete fix of R7-S1-M14: the cap chain came with 14fe5f5 and 41e803f, and the write-side throw with abeb47c. Before abeb47c the same plans gave a state the spine could not read, which also allowed.
- **Hand-made artefact:** no hand edit of a spine file. P1 needs an absurd agent-written READINESS.json, the same precondition as M14. P3 needs a modest plan plus an agent-written `.secrets/<name>` file. **Exotic host:** no. Graded MEDIUM, like M14.

Fix:
1. In `refuseOrPark` and `eachRefusal`, when the run's state was read and it has open rows but the refusal's `writeState` fails, **refuse anyway**: `STOP_REFUSED` with the refusal uncounted and `unwritable` noted, and not an allow. Do this at least for `STATE_TOO_LARGE`, and arguably for any write error once the open rows are known. Patience cannot advance then, so the owner also sees the error on stderr. The fail-open rule stays only for an unreadable state.
2. Give `planTooLarge` headroom, for example cap − 1 MiB, so normal growth and the gate's own fields never meet the cap. This alone does not cover P3 (redaction inflation).
3. Optional: redaction could refuse to register a value that would rewrite protocol-bearing state values (slice ids, `depends_on`). That is outside S1.
4. Regression test: the P1 plan at cap − 47 and the P3 plan plus a `.secrets` file → hook 2 with "STATE_TOO_LARGE" on stderr, and `gate stop` → `STOP_REFUSED`.
