## 3. Attack on the open-only dedupe (probe 4)

- **Rapid cycles (5 × park, answer, resume):** Q1 to Q5, each answered, never two open at once, events [1..5]. That is one question per park the owner answered, which is the M17 contract, so it is not a flood. The pack grows by one row per owner answer. Each row needs an `answer` plus a `resume`, so this is bounded by owner actions.
- **Resume without answering, then park:** the open question is reused (Q6, events [6, 6]).
- **I/O fault on the run folder** (`chflags uchg` on the folder): the pack write fails too, so nothing dangles. Hook 2, uncounted.
- **I/O fault on `state.json` only, then the rows change:** this leaves two open gate questions at once (R11-S1-L-h, below).

### R11-S1-L-h LOW: a dangling park question from an I/O fault survives a later park with changed rows, so two gate questions are open and `pack withdraw --by stop-gate` cannot remove the first

```
patience 1; park → answer → resume (Q1 answered, event [1]); one counted refusal
chflags uchg state.json; 2 stops       → hook 2,2; Q2 added (open), no stop_parked event, BUILDING
chflags nouchg; intake marked DONE      → hook 2 (sig changed, counter reset), hook 0 → PARKED, Q3 added
open gate questions: Q2 AND Q3; events [1, 3]
pack withdraw --by stop-gate            → PACK_WITHDRAWN [3]; Q2 stays open
```

Why it happens:
- Q2 was written by `packAppend` before `writeState` failed, so it never got a `stop_parked` mark. The L-f path is unchanged.
- When the rows change, the park text changes too. So neither the text dedupe nor the `held` (marks-based) branch recognises Q2, and the park adds Q3.
- `isStopGateQuestion` needs a mark, so the withdraw skips Q2.

Assessment:
- **Severity: LOW.** It needs an I/O fault between the pack write and the state write: a read-only `state.json`, or a disk that fills between the two writes. That is the same trigger as L-f.
- **It is not a false pass.** The refusals and the park are correct. Only the owner pack carries one stale, unmarked open question. The owner can still answer it.
- **Origin:** a residual of L-f that predates round 10. On a592f9f the same sequence also adds Q3, because the old skip rule needed a mark too. The open-only dedupe did not introduce it.
- **Docs:** the CHANGELOG L-f entry ("It is never more than one, and the next stop that can write parks the run and reuses it") holds only when the rows are unchanged, so it overclaims.
- **Hand-made artefact:** yes, a filesystem fault (`chflags`, or a full disk). **Exotic host:** no.
- **Fix, either one:** withdraw the just-added question in the park branch's `uncounted` path (r9 fix option a), or narrow the CHANGELOG wording to "until the rows change".
